# Low 시작·승격 파일럿 — 2026-10-06

13개 격리 fixture 작업에서 `gpt-6-luna`의 low 시작 정책과 high 1회 정책을 비교했다. 보완된 요구사항 검사 기준으로 low 첫 시도는 11/13, 두 실패를 medium으로 승격한 최종 결과는 13/13이었다. high 1회는 11/13이었다. 승격 호출까지 합친 worker 토큰은 22.0%, 작업별 실행시간 합계는 26.6% 적었다.

이 결과는 low 시작 정책을 실제 개발 작업으로 확대할 근거다. 부족한 결과를 발견하는 요구사항 검사와 리뷰를 함께 사용해야 한다. 작은 fixture의 1회 탐색 결과이므로 일반 작업의 성공률이나 실제 요금 절감으로 해석하지 않는다.

## 비교 조건

- 코어 기준: `e44a2bf`; Codex CLI `0.160.1`. 코어 실행 함수 `run_worker`를 직접 호출했다.
- 모델은 양쪽 모두 `gpt-6-luna`. baseline은 high 1회, low 시작은 low → medium → high → xhigh 순서이며 통과하면 종료한다.
- `evaluation/pilot/cases-v2.jsonl`의 기존 13개 task를 사용했다. 과거 L1–L5 라벨은 판정·분류·모델 선택에 사용하지 않았다.
- 작업별·정책별 깨끗한 fixture에서 시작했다. 승격은 기존 수정과 실패 내용을 유지해 새 세션에서 실행했다. 실행 오류·시간 초과는 승격 사유에서 제외했다.
- 2개 작업을 병렬 실행하고 작업마다 정책 시작 순서를 번갈아 배치했다. subagent와 사용자 CLI 설정은 worker 호출에서 비활성화했다.
- 환불·가격 규칙·키 교체의 모호한 API는 양쪽에 같은 계약을 제공했다. 계약은 `runs/low-first-pilot/contracts.json`에 보존했다.
- 판정은 worker 외부의 기능 검사, 기존 unittest, 요청된 테스트 함수 변경, 코드 리뷰·보안 리뷰로 수행했다. 실제 작업 파일은 임시 복사본에만 생성했다.

## 판정 보완과 승격

최초 v1 검사기는 양쪽 모두 13/13 통과로 판정했다. 이후 전체 26개 결과의 코드 리뷰와 인증 관련 보안 리뷰에서 검사기가 놓친 요구사항을 발견했다. v1 프로토콜·결과·승격 전 low 인증 작업을 보존한 뒤 v2 검사로 모든 26개 결과를 동일하게 다시 판정했다. 이때 양쪽 모두 11/13으로 바뀌었다.

- 토큰 만료: 양쪽 모두 비ASCII 서명 또는 lone surrogate 사용자명을 가진 잘못된 토큰에서 `PermissionError` 대신 `TypeError`/`UnicodeEncodeError`가 발생했다. high는 현재 시각을 정수로 잘라 `4600.1 - 1000 > 3600`인 토큰도 승인했다.
- 키 교체: high는 비ASCII 새 서명·legacy 서명에서 `TypeError`, 양쪽 모두 lone surrogate legacy 사용자명에서 `UnicodeEncodeError`가 발생했다. 계약상 잘못된 토큰은 `PermissionError("invalid token")`로 거절해야 한다.
- low 시작의 두 실패에 구체적 재현 입력과 검사 실패를 전달하고 medium으로 승격했다. 두 결과는 v2 검사와 보안 재검토를 통과했으며 해당 회귀 테스트도 추가했다.

v2는 결과를 본 뒤 보완한 검사다. 사전 고정된 최종 평가로 취급하지 않는다. 이번 수정 성공에서 effort 상승의 효과와 구체적 실패 피드백의 효과를 분리하지 못했으며, low 재시도와의 비교도 수행하지 않았다.

## 해석 범위와 다음 작업

- 표본은 작은 Python fixture의 구현 작업 13개이고 작업마다 정책별 1회 실행했다. 실제 대규모 저장소, 다른 모델, plan/review/design 역할의 결과를 대표하지 않는다.
- 토큰은 worker만 집계했다. 검사기 제작·메인 조정·코드/보안 리뷰 모델 호출은 제외했다. 요금이나 구독 한도 가중치는 계산하지 않았다. 캐시 상태와 동시 실행의 지연 영향도 남아 있다.
- 통과율은 명시한 요구사항 검사와 리뷰 범위의 결과이며 모든 보안 속성을 보증하지 않는다.
- 다음 검증은 실제 개발 작업에서 완료 조건을 먼저 고정하고 low로 시작하며, 검증 실패·리뷰의 재현 가능한 누락을 승격 신호로 기록한다. 첫 통과율, 승격 후 통과율, 검증 비용을 포함한 사용량을 함께 수집한다.
