# 조건부 Jev 재판정: 실제 연쇄 호출 검증 (2026-10-05 KST)

**실험용 연쇄 경로는 사전 기준을 통과했다.** 기존 300건에서 난이도 정확도 238/250(95.2%), critical miss 1/128, Jev 호출 168/300(56.0%)이었다. 새로 호출한 진단 입력의 리뷰 L2는 두 정보 조건 모두 8/8로 회복했다. 제품 코드·설정·질문·임계값·플러그인과 기존 코퍼스는 변경하지 않았다. 이 결과는 제품에 적용된 체인을 검증한 것이 아니며 독립 holdout 평가도 아니다.

## 고정 규칙과 실행

[이전 후보](l2-boundary-experiment-20261004.md)의 `guide + uncertain_or_scoped_or_risk`를 그대로 실행했다. Nimble이 먼저 성공하면 아래 조건 중 하나라도 참일 때만 같은 입력으로 Jev를 이어 호출한다.

- Nimble 원점수 top 확률 <0.60 또는 top 두 확률 차이 <0.15.
- Nimble이 예측한 target이 `plan_only` 또는 `review_only`.
- Nimble backend 위험 플래그 또는 기존 regex 위험 플래그가 존재.

선택에 정답 라벨을 사용하지 않았다. Jev를 호출하면 Jev의 레벨·target·backend 위험 플래그를 그대로 최종 결정에 사용한다. 위험과 세션 평가에는 기존 평가 함수가 regex 위험 플래그를 합친다. 최종 승격된 레벨이 아니라 원점수 확률을 선택에 사용한다.

기존 코퍼스 300건과 [의도·맥락 진단](intent-context-ablation-20261005.md)의 48개 고유 입력을 seed 20261005로 섞어 한 스트림에서 순차 실행했다. 진단의 기존 96행은 동일 입력 쌍 48개임을 assert했고 `r1`만 사용했다. 입력 하나에서 Nimble이 끝나기 전에 Jev를 시작하지 않았다. 단계별 timeout은 30초로, 두 단계가 모두 실행되면 최대 예산은 약 60초다. 제품의 fallback 함수는 사용하지 않았다. 그 함수는 Nimble 성공 시 조건부 Jev를 호출하지 않기 때문이다.

기존 보강 level 질문을 transport에서 교체하고 다른 질문은 동일함을 호출마다 assert했다. payload state가 task와 paths 전체를 담았는지도 assert하여 잘림을 배제했다. Nimble repo/user options는 None이었다.

## 호출 증거

| 항목 | 본 실험 결과 |
|---|---:|
| 입력 | 348 (코퍼스 300 + 진단 48) |
| Nimble 호출 | 348 |
| 조건부 Jev 호출 | 203 (코퍼스 168 + 진단 35) |
| 총 live 호출 | 551 |
| HTTP 200 | 551/551 |
| 응답 모델 | Nimble `nimble` 348, Jev `jev-1.13.0` 203 |
| 통신/파싱 실패·default fallback | 0 |
| 입력 토큰 | Nimble 3,067,572; Jev 221,873 |
| 출력 토큰 | Nimble 3,132; Jev 33,387 |

348개 전부에서 기록이 고정 순서와 일치했다. 선택된 203개는 정확히 `nimble → jev`, 미선택 145개는 Nimble만 있었다. 선택된 각 쌍의 payload state SHA-256이 동일했고 최종 결정이 선택된 backend 결정과 같음을 확인했다. 제품·플러그인·코퍼스·고정 질문은 호출 전후 파일 해시 전체가 동일했다.

본 실험 직전 첫 입력 시도는 호출 후 `mappingproxy` 확률 객체의 직렬화 오류로 중단됐다. 직렬화를 수정하고 실행 검사를 통과한 뒤 중단 산출물을 분리하고 전체를 새로 실행했다. 중단 시도의 응답·호출 수는 보존되지 않았으므로 위 551회에 포함하지 않으며, 이 숫자는 세션 전체 과금 횟수를 뜻하지 않는다.

## 기존 300건 결과

같은 실행에서 얻은 Nimble 첫 단계와 최종 연쇄 결정을 비교한다. 난이도 분모는 250건, target 분모는 300건이다.

| 항목 | 같은 실행 Nimble | 실제 연쇄 |
|---|---:|---:|
| 난이도 정확도 | 220/250 (88.0%) | 238/250 (95.2%) |
| target 정확도 | 289/300 (96.3%) | 294/300 (98.0%) |
| critical miss | 6/128 | 1/128 |
| L1–L3를 L4/L5로 과대승격 | 2 | 0 |

| 정답 레벨 | 실제 연쇄 정확도 |
|---|---:|
| L1 | 51/51 (100.0%) |
| L2 | 44/49 (89.8%) |
| L3 | 49/50 (98.0%) |
| L4 | 46/50 (92.0%) |
| L5 | 48/50 (96.0%) |

사전 기준인 레벨별 정확도 ≥80%, critical miss ≤2, 불완전 실행 0을 모두 만족했다. 기존 v1은 123/130(94.6%), critical 0, target 147/150이며 추가분은 115/120(95.8%), critical 1, target 147/150이다. 두 구간의 각 레벨도 80% 이상이다. Jev 호출은 각각 84/150이었다.

Jev 단독으로 같은 300건을 호출하는 경우와 비교한 **API 호출 수 절감은 44.0%**다. 전체 추론 호출은 300에서 468로 늘어나므로 전체 비용 절감이라고 해석하지 않는다. 토큰 합도 모델별 비용이나 로컬 연산 비용으로 환산하지 않았다.

이전 저장 결과 재생은 237/250이었고 이번에는 238/250이다. Nimble 레벨은 과거 300건과 동일했지만 선택된 Jev의 `add-063`이 L3에서 L4로 바뀌었다. 이는 새 live 출력의 차이이며 저장 결과를 그대로 복사한 결과가 아니다. 과거 Jev 단독 결과는 동시 대조군이 아니다.

남은 critical은 `add-041`이다. 정답 L2인 고정 로그 문장에서 비밀번호 값만 제거하는 작업을 Jev가 L1로 판정했다. `uncertain + risk`로 Jev에 넘겼지만 교정되지 않았다. 전체 과대평가 2건, 과소평가 10건이며 오답 목록은 analysis 원자료에 보존했다. 병합 위험 플래그는 TP 143, FP 81, FN 15로 재현율 90.5%, 정밀도 63.8%다.

## 진단 입력 48개 결과

각 행은 기반 예제 12개 중 L2 8개를 한 번씩 호출한 결과다. 앞선 보고서의 두 반복 16회와 분모가 다르다.

| L2 조건 | 같은 실행 Nimble | 실제 연쇄 | Jev 호출 (L1–L3 전체) |
|---|---:|---:|---:|
| 구현 · 설명+경로 | 6/8 (75.0%) | 8/8 (100.0%) | 6/12 |
| 구현 · 코드+diff 추가 | 5/8 (62.5%) | 7/8 (87.5%) | 5/12 |
| 리뷰 · 설명+경로 | 2/8 (25.0%) | 8/8 (100.0%) | 12/12 |
| 리뷰 · 코드+diff 추가 | 0/8 (0.0%) | 8/8 (100.0%) | 12/12 |

전체는 Nimble 29/48(60.4%)에서 연쇄 47/48(97.9%)로 개선됐다. target은 양쪽 모두 48/48이며 critical miss는 0/4다. 리뷰 요청 24개 모두 Jev로 넘어갔다. 콜백 구현+코드 예제의 Nimble L2→L5 후처리 오류도 Jev L2로 교정됐다.

남은 오답은 `intent-ctx-010-implement-current_code_and_recent_diff-r1`의 UTF-8/gzip JSON 로더이다. 정답 L2를 Nimble이 L1로 판정했고 선택 조건에 걸리지 않아 Jev를 호출하지 않았다. 확신 있는 비위험 구현 오답은 이 규칙이 놓칠 수 있다. 이번 진단에서 Jev 단독 48회 대비 호출 절감은 27.1%다.

## 실제 지연

monotonic clock으로 Nimble 시작부터 최종 단계 종료까지 측정했다. 서로 다른 실행의 지연을 더한 추정치가 아니다. p95는 정렬 값의 `floor(0.95*(n-1))` 인덱스를 사용했다.

| 범위 | p50 ms | p95 ms | 최대 ms |
|---|---:|---:|---:|
| 코퍼스: 같은 실행 Nimble 단계 | 1,035.5 | 1,154.6 | 1,310.6 |
| 코퍼스: 실제 연쇄 전체 | 1,165.5 | 1,415.8 | 1,698.0 |
| 코퍼스: 선택 168개 전체 | 1,287.2 | 1,443.0 | 1,698.0 |
| 코퍼스: 미선택 132개 전체 | 1,044.8 | 1,154.7 | 1,310.6 |
| 코퍼스: 선택된 Jev 단계 | 255.8 | 385.0 | 706.9 |
| 진단: 실제 연쇄 전체 | 1,327.0 | 1,548.6 | 1,675.3 |

조건부 Jev는 추가 순차 지연이 있다. 선택된 Jev 단계는 어려운 요청에 치우친 부분표본이므로 Jev 단독 전체의 지연으로 해석하지 않는다. 모델 warm/cold 상태를 통제하지 않았으며 실제 사용자 동시 부하의 큐 지연도 측정하지 않았다.

## 실패 처리 검사와 한계

네트워크 없는 모의 검사 8개와 기존 Jev/Nimble/chain 검사 71개가 통과했다. 선택/미선택 호출 수, 동일 입력과 단계 timeout, 원점수 기준 선택, scoped/regex 위험 선택을 확인했다. 실험 경로의 실패 정책은 Nimble 실패 시 Jev를 시도하고, 선택된 Jev 실패 시 오류를 기록한 default L3를 반환한다. 둘 다 실패한 경우 두 오류 원인을 보존한다. 실패 실행은 정상 정확도 통과로 취급하지 않는다. 이는 실험의 고정 정책이며 제품 운영 정책으로 채택한 것이 아니다.

live에서는 실패가 없어 실제 네트워크 장애·30초 deadline 도달을 유발한 검증은 하지 않았다. 모의 검사는 호출 경로를 확인하며 실제 장애 복구 품질을 입증하지 않는다. Python 검토자는 수정 후 실험을 무효화할 CRITICAL/HIGH 문제를 발견하지 않았다. 검사 파일은 구현 후 추가됐으므로 RED→GREEN TDD 완료라고 주장하지 않는다.

300건은 후보 선정에 이미 사용됐고, 48개도 앞선 진단에 노출된 12개 기반 예제의 네 변형이다. AI 합의 정답이며 사람 검증과 실제 요청 holdout은 없다. 따라서 이번 결과는 조건부 호출의 실행·지연과 알려진 표본에서의 개선을 확인한 것이다. 제품 채택 전에 사람의 경계 라벨 검토와 새 실제 요청 holdout이 남아 있다.

## 원자료와 재현

ignored `runs/`에 있으므로 이 문서만 공유해도 원본이 함께 공유되지는 않는다.

- 실행 코드: `runs/conditional_chain_20261005.py`; 모의 검사: `runs/test_conditional_chain_20261005.py`.
- 고정 계획·입력 순서·보호 파일 해시: `runs/conditional-chain-20261005-plan.json`.
- 최종·단계별 결정: `runs/conditional-chain-20261005-records.jsonl`.
- 원응답·HTTP 상태·payload 해시·transport 시간: `runs/conditional-chain-20261005-traces.jsonl`.
- 기본 집계: `runs/conditional-chain-20261005-summary.json`; 조건·구간·같은 실행 대조·감사: `runs/conditional-chain-20261005-analysis.json`.
- 중단 시도: `runs/conditional-chain-20261005-aborted-serialization-*`.

```sh
python3 runs/conditional_chain_20261005.py
python3 runs/test_conditional_chain_20261005.py -v
python3 -m unittest tests.test_jev tests.test_nimble tests.test_chain_registry -q
```

첫 명령은 dry-run이다. `--live`는 외부 API 호출이며 동일 산출물이 있으면 덮어쓰지 않고 거부한다. 재실행 시 별도 출력 prefix를 사용해야 한다.
